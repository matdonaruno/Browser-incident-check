# 入力インシデント防止 設計書 (ドラフト)

作成: 2026-10-07 / ステータス: 設計段階 (L0 のみ実装済み、L1・L2 は未実装)

## 1. 目的

人が元データを見ながらWebフォームに入力する工程で、**入力ミスを送信前に知らせ、何が入力されたかをログに残す**。
元データを直接アップロード・インポートできない (紙、別システム、取り込み機能がない) 状況を前提にする。

特定業務 (精度管理サーベイ) に限定せず、「項目 → 値」の照合として一般化する。最初の適用先は臨床検査の外部精度管理サーベイ入力。

## 2. 問題の分解

意図 (何を入力しようとしているか) はブラウザから観測できない。元データを、入力とは別の経路で取り込んで初めて検証できる。

| # | 問い | 性質 | 手段 |
|---|---|---|---|
| 1 | この枠は、元データのどの項目に当たるか | 意味の対応 (表記揺れあり) | 辞書 + 類似度 → 人が確認して保存。AI は後段 (§6) |
| 2 | 入れた値は、その項目の元データの値と同じか | 機械的 | 文字列・数値の比較 |
| 3 | 入れた値は、別項目の元データの値と一致していないか (入れ違い) | 機械的 | 値の逆引き |

## 3. 3段階の構造

| 段階 | 前提 | 内容 | 状態 |
|---|---|---|---|
| L0 記録 | 元データ不要 | 入力・貼り付け・送信のログ。許可サイトでは値・修正履歴・送信時スナップショット | 実装済み (実ブラウザ未確認) |
| L1 ルール検査 | 元データ不要 | 正解を知らなくても分かる異常の検知 | 未実装 |
| L2 照合 | 元データあり | 元データとの突き合わせ。#1〜#3 | 未実装 |

3段階とも、送信前に1つの**ゲート**で結果を見せる (§5)。

### L1 の検査項目 (候補)

- 貼り付けた内容と、欄に入った値の差 (maxlength による切り捨て、入力マスクによる書き換え、全角半角変換)
- 貼り付けの異常: 改行・タブ・前後空白・不可視文字、複数行・複数セルの貼り付け、先頭 0 の欠落
- 取り違えの兆候: 隣の欄と同じ値、同じ値が別欄にもある、貼り付けによる既存値の上書き
- 形式: 数値欄に単位や文字が混入、前回値から桁が大きく外れる

優先順位は、実際に起きたコピペ事故の聞き取り後に確定する (§9)。

## 4. 元データの入口 (差し込み式)

照合ロジックは1つ。入口を複数持つ。

1. 表をコピーして、拡張のサイドパネルに貼る (最初に作る)
2. CSV / Excel ファイルを拡張に読ませる (サイトには送らない)
3. 画像を OCR で読む
4. 手入力 (二重入力)

データモデルは「項目 → 値」のリスト。表は、同じ項目が繰り返される形として扱う (行名 + 列名をキーにする)。
表に特有なのは「別の行の値と一致している」ことの検知だが、これは #3 の特殊形で、専用機能は足さない。

## 5. 送信前ゲート

- 入力一式と元データを並べて表示
- 警告 (不一致、入れ違いの疑い、L1 の検出) を目立たせる
- 全警告を確認するまで送信させない (Gmail送信前確認の作法を踏襲)
- 確認した事実 (誰が・いつ・どの警告を確認したか) をログに残す
- ツールは判定しない。最終判断は人。誤警告は確認が1回増えるだけ、見逃しが本当のコストなので、疑わしきは警告に倒す

## 6. 項目の対応づけ (#1) の方針

**最初は決定的な方式。** 表記辞書 (GLU = グルコース = 血糖) と文字列類似度で候補を出し、人が確認して対応表を保存。2回目以降は対応表で自動。

**Jev は影で並走させる** (`jev-decisions` の手順)。

1. 既存の判定を動かしたまま、同じ入力を Jev にも通してログに残すだけ
2. 一致率と食い違いを実際に読む
3. 納得できたら、新しいフォームの対応づけ提案の自動化に使う

5条件の検算結果: 件数の条件が弱い (対応づけは1フォーム1回、保存すれば再利用)。多数のフォーム・利用者に配る段階で価値が出る。

- 確率は人に回す基準にする。個々の正しさの保証にはならない。承認は常に人が行う
- `verification_needed` を同時に聞く。高ければ人に回す
- 送るのは**項目名のみ**。値は送らず、比較はブラウザ内で行う
- API キーは拡張に埋め込めない (コードが読めるため)。中継サーバか、利用者自身のキー設定にする
- ブラウザ内蔵 LLM (端末内完結) も候補。対応状況・精度は**未確認**

## 7. ログ

- 保存先: `chrome.storage.local` (端末内のみ、外部送信なし)
- 既定はメタデータのみ。許可リストに入れたサイトでだけ値・修正履歴・スナップショットを保存
- パスワード欄は常に対象外
- L2 導入後に追加: 元データのスナップショット、照合結果、警告の確認記録
- 値を含むログは機密の保管場所になる。保管期限・削除の運用は利用施設で決める (現状は手動の全削除のみ)

## 8. 既存ツールとの関係 (調査結果、網羅ではない)

元データ照合 + 送信前通知 + ログを一体にした既製品は、調べた範囲では見つからなかった。近い部品は以下。

| 種類 | 例 | 足りない点 |
|---|---|---|
| 貼り付け時の DLP | Chainstack DLP (OSS)、Paste Shield、SafeRelay | 目的が情報漏えい対策。入力の正しさは見ない |
| 貼り付け支援 | Cross Paste | 値の正しさ、ログがない |
| 送信前確認 | Gmail 送信前確認 | Gmail 専用 |
| 入力の保全 | Typio Form Recovery、form-safe | 検証しない |

未調査: Edge Add-ons、企業向けの操作ログ製品 (セキュリティ監査寄りと推測、未確認)。

## 9. 参考事例 (二次資料。一次資料は未確認のものを含む)

- TransAlta: Excel の行ずれで入札が別契約に対応づき約2,400万ドルの損失 (Teampay の資料)
- JPモルガン: 手作業のコピペで回る Excel モデルと計算式の誤り。コピペ単独が原因とは言えない (タスクフォース報告書の解説記事)
- 診療記録のコピペ由来の誤り 8.3% (AusDoc の記事が引く研究)
- 臨床検査データの手入力の転記誤り率は低い1桁%程度の報告が多い (JAMIA)
- 二重入力は読み上げ方式より誤りが少ないとする研究あり (要約を読んだのみ)

共通点は、値の誤りというより**値が別の対象に付く**形のミスが目立つこと。#3 の根拠。

## 10. 未決事項

1. 実際のコピペ事故の中身 (TEPPAN の件。検索では見つからず、利用者への聞き取り待ち)。L1 の優先順位を決める
2. 実サイトの入力画面の構造 (個人情報・ログイン情報を除いた保存ページ)。対応づけの設計に必要
3. 実機での動作確認 (Chrome / Edge、実サイト)。L0 は擬似フォームでのみ確認済み
4. 外部 API (Jev) 利用時の情報規程上の可否
5. ログの保管期限と運用

## 11. ロードマップ

1. L0 の実機確認と実サイトでの調整
2. 送信前ゲート (L0 のスナップショットを並べて表示 + 確認記録)。元データなしでも価値がある
3. L1 ルール検査 (事故の聞き取り後)
4. L2 照合 (サイドパネルへの貼り付け入口から。対応表は人が確認して保存)
5. Jev の影での並走 → 結果次第で対応づけ提案に採用
